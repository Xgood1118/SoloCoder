# Python CRM同步服务

## 背景与痛点

我们销售团队一直在用两套系统，一套是自研的CRM系统，另一套是从厂商买的营销自动化平台，两个系统的客户数据一直没法自动同步，全靠运营手工导Excel导入，每个月光导入导出就要耗费好几个人天，而且特别容易出错，数据口径不一致的时候销售和营销两边对不上，经常互相扯皮。更要命的是数据同步是T+1的，营销活动的效果数据第二天才能看到，等发现线索凉了黄花菜都凉了。这次要把同步链路打通，做到准实时同步，数据延迟控制在5分钟以内，而且要保证数据一致性，不能出现这条数据在CRM是张三但在营销平台是李四的情况。

## 功能需求

客户主数据同步是基础。CRM里客户信息包括基本信息（公司名、地址、联系人）、客户等级、行业分类、跟进状态等，营销平台那边也有对应的字段，两边的字段映射关系要可配置，不能写死。因为两个系统的客户唯一标识不一样，CRM用自增ID，营销平台用UUID，同步的时候要做映射表，记录每条记录在两边的ID对应关系。新增客户时先在CRM创建，然后同步到营销平台，营销平台返回的ID要回写到映射表。更新时也要走这个映射表，不能搞错。

联系人数据同步要单独处理，一个公司下面有多个联系人，每个联系人的手机号、邮箱、职位、部门都要同步。联系人有个特殊逻辑是默认联系人的概念，每个公司有一个默认联系人，同步时要保持这个标记一致。另外联系人有离职调岗的情况，离职之后在CRM会标记为非活跃，同步到营销平台时要处理这种状态映射，有些平台没有非活跃状态，就需要决定是同步过去还是跳过。

销售线索同步是这次的重点。营销平台产生的线索要同步到CRM作为跟进对象，CRM里已经有一些线索数据，这两个数据源有时候会有冲突，比如同一个手机号在两边都有记录但公司名称不一致，这时候要做合并判断。合并策略建议先按手机号匹配，如果手机号一样但公司名不一样，提示运营手工确认。线索同步过来之后，CRM这边要给线索分配负责人，默认按区域或者行业分配，也可以指定规则。

商机和订单数据也要反向同步回去。CRM里商机跟进到签约阶段，要在营销平台里标记为成交用户，触发相应的营销动作（比如发送复购优惠、加入VIP群等）。签约金额、签约日期、合同期限这些信息也要同步过去，方便营销平台做客户画像和复购预测。数据流向是双向的，所以要有防循环同步的机制，建议在数据里加一个 sync_source 标记，标明数据的原始来源，流转时检查这个标记。

同步任务调度要支持多种触发方式。一种是定时同步，按cron表达式配置，支持按分钟、小时、天运行；另一种是变更触发，当CRM数据发生变化时立即推送，这次优先用变更数据捕获（CDC）的方式，如果CRM支持的话就用binlog解析，不支持的话就在应用层做事件监听；第三种是手工触发，运营可以在后台手工触发一次全量同步或者指定范围同步，用于修复数据问题。调度框架建议用 APScheduler 或者 Celery Beat。

同步日志和监控告警要做好。每次同步操作要记录同步了什么表、多少条记录、耗时多少、是否有错误，错误记录要包括错误类型和错误明细，方便排查。全量同步完成之后要给运营发一条汇总通知。如果同步延迟超过阈值（比如5分钟内没追上增量），要触发告警，推送到钉钉或者企业微信。数据一致性校验也要做，定期跑一次全量数据对比，检查两边数据是否一致，发现不一致的记录告警出来让运营确认。

数据清洗和转换规则要灵活。两个系统的数据格式经常不一样，比如日期格式（2024-01-01 vs 2024/01/01）、手机号格式（带不带86前缀）、金额单位（元 vs 万元），这些转换规则要支持在配置里写，不用改代码。有些字段在一边有另一边没有，这时候要决定是填默认值还是空值还是跳过，这个也要可配置。

## 模块设计

整体用 Python 写，建议用 FastAPI 做接口层，给运营提供手工触发同步、查看同步状态、配置字段映射的管理后台。核心同步逻辑放在 service 包，按数据领域分成 customer_sync、contact_sync、lead_sync、order_sync 几个模块。基础设施放在 infrastructure 包，数据库访问用 SQLAlchemy，对接CRM和营销平台各写一个 Adapter。调度用 Celery，任务定义在 tasks 包。配置管理用 pydantic_settings，所有配置项都做校验，不接受非法配置启动。

建议把同步逻辑做成管道式的：Source（读取源数据） -> Transformer（数据转换清洗） -> Target（写入目标系统） -> Verifier（校验一致性），每个环节都是可插拔的，方便扩展新的数据源或目标。这种管道设计跑集成测试的时候也好 mock。

## 数据库设计

映射表是核心，表结构大概是这样：local_id、remote_id、entity_type、last_sync_time、sync_version、status。sync_version 用来做乐观锁，防止并发更新时覆盖问题。status 标记这条映射是否有效，有些客户在CRM删除了但营销平台没删，映射表里就要标记为软删除，不物理删除，方便对账。

同步日志表按天分区，记录每次同步任务的执行情况，包括 task_id、entity_type、operation_type（INSERT/UPDATE/DELETE）、record_count、duration_ms、status、error_detail。全量同步任务要单独记录，因为全量同步时间跨度长，需要记录进度。

## 边界条件与异常处理

网络抖动是最常见的异常，同步过程中如果目标系统接口超时或者报500，不能直接抛掉，要设计重试机制，重试策略建议用指数退避，比如第1次等1秒、第2次等2秒、第4次等4秒，最多重试5次。每次重试前检查目标系统是否可用，可以用探活接口先测一下。

数据循环同步是个大坑，两个系统互相推送，如果没加防护就会陷入死循环。建议的做法是：每条数据记录里加一个 origin 系统标记，从CRM推出去的数据标记为 from_crm，收到营销平台回传的数据时先检查这个标记，如果是 from_crm 的就不要再推回去了。另外同步去重也要做好，同样一条记录可能在很短的时间窗口内被修改了多次，只取最新的一次。

字段映射配置错误会导致数据错乱，比如把客户等级映射到了行业字段，同步过去就全乱了。建议在配置保存时做预校验，自动跑一些测试用例，检查映射后的数据是否合法。另外上线前要做一次数据质量扫描，把存量数据里不符合目标系统格式要求的标记出来提前清洗。

并发同步要小心，全量同步和增量同步同时跑的时候，要保证增量数据不被覆盖。建议用分布式锁控制，同一时间只有一个同步任务在运行，或者用任务队列做串行化。

时间窗口问题也要注意，有些字段的更新时间可能会有时区问题，建议所有时间统一用 UTC 存储，在展示层转成本地时间。另外同步任务的调度时间要避开业务高峰期，比如月初月末财务跑账的时候不要跑全量同步。

## 技术选型

Web 框架用 FastAPI，ORM 用 SQLAlchemy，任务队列用 Celery + Redis，HTTP 客户端用 httpx 或者 requests，CSV/Excel 处理用 pandas，日期处理用 python-dateutil，时区用 pytz，日志用 loguru 或者 standard logging + structlog。

## 测试与部署

单元测试用 pytest，集成测试用 Testcontainers 起 MySQL 和 Redis。同步逻辑要跑回归测试，每次改动之后自动跑一遍历史同步记录，确保不会 regression。部署用 Docker，镜像推送到私有仓库，K8s  Deployment 管理副本数，设好 resource limits 和 liveness probes。
