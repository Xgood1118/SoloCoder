# 服务发现与注册管理系统

## 背景

微服务架构下，服务实例动态启停，客户端需要知道当前有哪些可用实例。我们需要一个服务注册与发现系统，支持服务注册、健康检查、按标签路由、加权负载均衡、服务依赖管理与实例级指标收集。

## 核心功能

### 1. 服务注册与实例管理

服务注册接口：POST /api/v1/services，body 包含 name（服务名）、host、port、tags（数组，如 ["v2","prod","us-east"]）、metadata（kv 对象，如 { "weight": 2, "az": "us-east-1a" }）。同一个服务名可以注册多个实例（host:port 组合），每个实例有唯一 instance_id（UUID）。注册时如果 host:port 已经存在则更新已有实例，不创建新的。返回 201 创建成功或 200 更新成功，body 里包含 instance_id。服务实例有生命周期状态机：pending -> healthy -> unhealthy -> removed。注册成功初始为 pending，等第一次健康检查通过后转为 healthy。实例列表支持 GET /api/v1/services?name=xxx&tags=v2 过滤，tags 过滤支持 AND（多个 tag 同时满足）和 OR（逗号分隔表示满足任一）。

### 2. 健康检查与状态流转

系统每 15 秒对所有 pending 和 healthy 实例做 TCP 端口检测，超时 3 秒视为失败。状态流转规则：pending 状态下连续 2 次失败转为 unhealthy；healthy 状态下连续 3 次失败转为 unhealthy；unhealthy 状态下连续 2 次成功转为 healthy；已 removed 的实例不再检查。实例状态变化时记录时间戳到 last_transition_at 字段。健康检查结果写入每个实例的 health_history（最多保留最近 50 条），每条记录包含 timestamp、status（pass/fail）、latency_ms。实例转为 unhealthy 后仍保留在列表里但不参与负载均衡，直到恢复。如果一个实例连续 10 次检查都失败，系统自动将其标记为 dead（unhealthy 的子状态），不再自动恢复，必须人工干预。

### 3. 服务依赖管理

服务可以声明依赖关系：PUT /api/v1/services/:id/dependencies，body 包含一个 dependency 列表（每个元素是 { name: "依赖服务名", min_healthy: 数字 }）。系统要求依赖服务的 healthy 实例数不能低于 min_healthy，如果低于则本服务所有实例降级为 degraded 状态（healthy 的子状态，不参与负载均衡但在列表里可见）。依赖检查每 30 秒运行一次。删除依赖关系的接口：DELETE /api/v1/services/:id/dependencies。移除一个服务实例时，如果该实例有其他服务依赖它，系统拒绝移除并返回 409 Conflict，报错信息包含依赖当前健康实例数和要求的最少数量。解除依赖需要先清空 dependency 列表才能删除服务。

### 4. 负载均衡与路由

负载均衡接口：GET /api/v1/discover/:serviceName，返回可用实例列表（过滤掉 unhealthy/degraded/dead）。默认策略是加权随机（每个实例 weight，默认 1），选中概率 = weight / sum(weights)。被选中后该实例 weight 减 1，其他实例 weight 加 0.5，实现请求分散。提供策略切换：GET /api/v1/discover/:serviceName?strategy=round_robin（轮询，按 instance_id 字母顺序循环）或 strategy=least_connections（最少连接，随机返回健康实例里 health_history 最近 5 条平均延迟最低的）。策略参数通过 query string 传递，实例记住上次使用的策略。标签路由：GET /api/v1/discover/:serviceName?tags=v2,us-east 将结果限制在匹配标签的实例里。如果指定了 tags 但没有匹配实例，返回 404 并提示 "no instances match tags"。

### 5. 实例级指标收集

每个实例维护运行时指标：最近请求数（每分钟窗口）、平均延迟、最近错误率（最近 50 条健康记录里 fail 的比例）、最后一次响应时间。指标通过 POST /api/v1/services/:id/metrics 更新（通常是服务本身回调报告），body 包含 requests_count、avg_latency_ms、error_count。这些指标不影响健康检查状态，但影响负载均衡策略（如 least_connections 依赖 avg_latency）。指标数据在内存维护，每个实例保留最近 60 条数据点，超出则 FIFO 丢弃。

### 6. 服务分组与命名空间

支持命名空间隔离：所有接口增加 namespace query 参数，默认为 default。同一命名空间内服务名唯一。namespace 相同的服务才能相互设置依赖关系（跨命名空间依赖返回 400）。命名空间列表：GET /api/v1/namespaces，返回所有有注册实例的命名空间。

### 7. 批量操作

批量注册：POST /api/v1/services/batch，body 包含 services 数组（每个元素同注册参数），原子处理（全部成功或全部失败），返回每条记录的 instance_id。批量下线：POST /api/v1/services/bulk-unregister，body 包含 instance_ids 数组，一次性移除多个实例。

### 8. 持久化

所有数据存在内存 Map 中（结构：namespace -> serviceName -> instanceId -> instanceData）。提供 export 接口：GET /api/v1/export，返回完整数据结构 JSON。提供 import 接口：POST /api/v1/import，body 为 export 格式数据，全量覆盖现有数据（用于服务重启后恢复）。所有写操作（注册/状态变化/依赖变更）自动写入操作日志到内存 append-only 列表，供 export 使用。服务端口从环境变量 PORT 获取，默认 8080。

### 9. 服务元数据管理

每个实例可以附加键值对元数据，通过 PATCH /api/v1/services/:id/metadata 更新（只更新指定 key，不影响其他 key）。元数据用于存储实例的版本号、负责人联系方式、自定义标签等辅助信息。GET /api/v1/services/:id/metadata 查看所有元数据。PATCH 时如果 key 不存在则创建，存在则覆盖。

### 10. 服务实例手动标记

支持 PUT /api/v1/services/:id/state 手动修改实例状态，比如人工将一个 dead 实例标记回 unhealthy（让它重新进入自动恢复流程），或者将 healthy 实例标记为 draining（不再接收新请求，但保留到现有请求完成）。健康检查仍然运行，但 draining 状态下的实例会被 discovery 接口过滤掉。手动标记不受自动状态机规则约束，允许自由跳转任何状态。标记变化不写 health_history，只更新 current_state 和 last_transition_at。

## 模块设计

拆分五个模块：

- registry.js：服务注册/注销、实例管理（in-memory map CRUD）
- health.js：健康检查调度器（定时任务 + 状态机流转）
- discovery.js：服务发现/负载均衡策略（加权随机/轮询/最少连接）
- router.js：依赖管理 + 命名空间 + 批量操作
- server.js：入口，Express 路由注册，middleware

server.js 依赖 registry.js 读写数据，registry.js 依赖 health.js 推送状态变化事件，discovery.js 依赖 registry.js 读取实例列表，router.js 依赖 registry.js 做依赖检查和数据导入导出。注意 registry.js 的写操作（注册/状态变更）需要原子性，同一服务名的多个并发写操作不能互相覆盖，使用 JavaScript Map 的原子性保证。

## 启动方式

node server.js 启动。三个环境变量：PORT（默认 8080），HEALTH_INTERVAL_MS（默认 15000），DEPENDENCY_INTERVAL_MS（默认 30000）。不依赖第三方包（Node.js 内置 http/https/os/url/dns 模块可用）。
